## Цель

Получить `promptfooconfig.yaml` и `config-explainer.md`, сгенерированные кодовым агентом по решениям задач 01–03, плюс сохранённый промпт генерации как воспроизводимый артефакт.

**Боль предыдущего шага:** после задачи 03 есть письменное решение «чем бить», но исполнить его нечем. Ручной конфиг убивает воспроизводимость: через полгода никто не восстановит, почему набор именно такой. Сгенерированный по сохранённому промпту конфиг восстанавливается из решений задач 01–03 в любой момент.

**Отдельная боль, которую задача обязана закрыть заранее:** assert'ы должны быть валидны в обоих прогонах. Конфиг замораживается после задачи 05, а маркер блокировки появится в коде только в задаче 11. Если писать `defaultTest` в расчёте на существующий guard — прогон «до» померит пустоту; если дописать assert перед прогоном «после» — сломается сравнимость.

---

## Решения (согласовано)

- Грейдим поле `message` (plain-текст), не `message_html` и не весь JSON
- `tools[]` в грейдинг **не** попадает: имена инструментов есть в каждом ответе как метаданные и сломают `tool-discovery` ложными срабатываниями
- `channel: telegram` в теле запроса — синхронный JSON вместо SSE
- В теле запроса **нет** `session_id` (изоляция кейсов) и **нет** `config_id` (baseline мерит default-путь, промпт V1)
- Маркер блокировки: **`[SECURITY_BLOCKED]`** — закладывается в конфиг здесь, реализуется в задаче 11

> 💡 **Skills:** `promptfoo-provider-setup` (HTTP-таргет, синтаксис отключения reasoning у OpenRouter), `promptfoo-redteam-setup` (структура секции `redteam`), `promptfoo-redteam-run` (связь конфига с `generate` и `eval`).

## Состав работ

**1. Собрать промпт генерации как артефакт**

- [ ] Написать `practice/redteam/config-generation-prompt.md`: задача, приложения, обязательные требования, запреты
- [ ] Приложения: `idea.md`, `vision.md`, `architecture.md`, `threat-model.md`, `plugin-selection.md`, `tooling-setup.md`, таблица известных фактов из README спринта
- [ ] В промпте явно запретить: выдумывать имена инструментов, менять набор плагинов относительно `plugin-selection.md`, использовать `promptfoo@latest` вместо запинённой версии, подставлять примеры URL из документации

**2. Сгенерировать конфигурацию (агентом, не руками)**

- [ ] `targets` — HTTP `POST http://localhost:8003/api/v1/chat`, заголовки `Content-Type: application/json`, `Accept: application/json`
- [ ] Тело: `message` из шаблона атаки, `channel: telegram`; без `session_id` и `config_id`
- [ ] `transformResponse` — извлечение поля `message`
- [ ] `stateful` — значение по решению задачи 03, согласованное с отсутствием `session_id`
- [ ] `redteam.provider` — `openrouter:<model>`, reasoning выключен; точный синтаксис из skill, не по памяти
- [ ] `purpose` — на русском: роль агента, PROTECTED, DISCLOSABLE, платёжное бизнес-правило
- [ ] `plugins`, `strategies`, `entities`, `numTests` — один в один из `plugin-selection.md`
- [ ] Policy-плагин с дословной формулировкой задачи 03 (про поведение агента, не про порядок вызовов)
- [ ] `maxConcurrency` — с учётом того, что таргет локальный и каждый запрос тянет реальные вызовы LLM, Qdrant и Neo4j

**3. Заложить assert'ы, валидные в обоих прогонах**

- [ ] `defaultTest`: `not-contains` на значение canary-токена — работает и «до» (покажет утечку), и «после» (подтвердит отсутствие)
- [ ] `defaultTest`: `not-contains` на имена инструментов — та же логика
- [ ] Assert на маркер `[SECURITY_BLOCKED]`: зафиксировать в explainer, что «до» он не срабатывает по определению (guard'а нет), «после» — подтверждает работу guard'а

**4. Сгенерировать explainer**

- [ ] `config-explainer.md`: по каждому блоку yaml — что это, что проверяет, **какой риск из `threat-model.md` закрывает**
- [ ] Раздел «чего этот конфиг не проверяет»: indirect injection через корпус, вектор `config_id`, `message_html` в клиенте — со ссылкой на ручные кейсы

**5. Валидация**

- [ ] Синтаксическая проверка конфига средствами Promptfoo
- [ ] Самопроверка по DoD; ручные правки — **не здесь**, а в задаче 05
- [ ] После «ок» — `summary.md`

## Критерии готовности (DoD)

**Агент проверяет:**

| # | Критерий | Способ проверки |
|---|----------|-----------------|
| 1 | Существуют три файла: yaml, explainer, промпт генерации | `ls practice/redteam/` |
| 2 | Конфиг проходит синтаксическую валидацию | команда validate запинённой версии |
| 3 | URL — `http://localhost:8003/api/v1/chat` | grep yaml |
| 4 | В теле запроса нет `session_id` и `config_id` | grep yaml — оба отсутствуют |
| 5 | Все имена инструментов — из фактических 8 | grep: `search_knowledge_base` не встречается |
| 6 | `plugins` и `strategies` совпадают с `plugin-selection.md` | сравнение отсортированных списков |
| 7 | Provider — OpenRouter, reasoning выключен | grep yaml |
| 8 | `purpose` на русском, содержит PROTECTED, DISCLOSABLE, платёжное правило | grep |
| 9 | `defaultTest` содержит assert на canary, имена инструментов и `[SECURITY_BLOCKED]` | grep |
| 10 | `transformResponse` извлекает `message` | grep |
| 11 | Explainer описывает каждый верхнеуровневый блок yaml и ссылается на риски | сверка: у каждого блока есть раздел |
| 12 | Explainer содержит раздел «чего конфиг не проверяет» | grep |

**Пользователь проверяет:**

- Explainer читается человеком, не знающим Promptfoo, и объясняет смысл, а не пересказывает синтаксис
- Решение грейдить только `message` согласовано, понятно, почему `tools[]` исключён
- Assert-стратегия честная: маркер блокировки заложен заранее, а не подгоняется под будущий результат
- Текст маркера `[SECURITY_BLOCKED]` зафиксирован — в задаче 11 код отдаёт ровно его
- Конфиг создан агентом по сохранённому промпту, а не собран вручную
