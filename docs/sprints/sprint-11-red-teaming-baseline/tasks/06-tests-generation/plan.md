## Цель

Получить `redteam-tests.yaml` командой `redteam generate` по замороженному конфигу и зафиксировать контрольную сумму — набор кейсов, который переживёт оба прогона без изменений.

**Боль предыдущего шага:** после задачи 05 конфиг проверен, но это описание намерения, а не сами атаки. Пока их нет, нельзя ни оценить качество проверки, ни зафиксировать baseline — `redteam eval` нечего исполнять.

**Почему отдельный шаг:** набор сценариев должен стать артефактом на диске, а не порождаться заново при каждом прогоне. Поэтому спринт запрещает `redteam run` — он генерирует и прогоняет в один проход, и «после» сравнение пойдёт на других атаках при полной уверенности, что атаки те же. Разделение `generate` → `eval` — техническая основа сравнимости baseline.

> 💡 **Skills:** `promptfoo-redteam-run` — различие `generate` / `eval` / `run`, флаги вывода, куда пишется набор кейсов.

## Состав работ

**1. Проверить предусловия заморозки**

- [ ] Сверить sha256 `promptfooconfig.yaml` со значением в `config-review-checklist.md` — конфиг не менялся после ревью
- [ ] Убедиться, что backend поднят и `/health` отвечает: часть плагинов при генерации обращается к таргету за контекстом
- [ ] Зафиксировать в логе: запинённая версия Promptfoo, commit репозитория, дата

**2. Генерация**

- [ ] `practice/redteam/node_modules/.bin/promptfoo redteam generate -c practice/redteam/promptfooconfig.yaml` с выводом в `practice/redteam/redteam-tests.yaml`
- [ ] Полный stdout/stderr → `practice/redteam/generate-log.txt`: там видно, сколько кейсов дал каждый плагин и где генерация деградировала
- [ ] При падении генерации **не** править `redteam-tests.yaml` руками: возврат в задачу 05, правка конфига, пересчёт sha256

**3. Сверка с бюджетом**

- [ ] Посчитать фактическое число кейсов и сопоставить с оценкой из `plugin-selection.md`
- [ ] Расхождение больше чем в 1.5 раза — разобраться в причине (неверный множитель стратегий либо плагин молча не отработал), а не принимать как есть
- [ ] Проверить, что кейсы появились **по каждому** заявленному плагину: пустой плагин здесь = вечное «не воспроизвелось» в задаче 09

**4. Заморозка набора**

- [ ] Посчитать и записать sha256 `redteam-tests.yaml`
- [ ] Зафиксировать правило: файл не редактируется до конца спринта; изменение требует повторной генерации и перезапуска **обоих** baseline
- [ ] Самопроверка по DoD; после «ок» — `summary.md`

## Критерии готовности (DoD)

**Агент проверяет:**

| # | Критерий | Способ проверки |
|---|----------|-----------------|
| 1 | `redteam-tests.yaml` существует и непустой | `ls`, число строк > 0 |
| 2 | sha256 конфига совпадает со значением из задачи 05 | сравнение с чек-листом |
| 3 | Лог генерации сохранён | `ls practice/redteam/generate-log.txt` |
| 4 | В логе зафиксированы версия Promptfoo и commit | grep по логу |
| 5 | Кейсы есть по каждому плагину из конфига | группировка в yaml, сверка со списком плагинов |
| 6 | Фактическое число кейсов сопоставлено с оценкой бюджета | раздел в логе или `summary.md` |
| 7 | sha256 `redteam-tests.yaml` зафиксирован | запись в логе |
| 8 | Файл не редактировался вручную | `git status` — единственное изменение внесено командой генерации |

**Пользователь проверяет:**

- Использована команда `generate`, а не `run` — и понятно, почему это принципиально для сравнимости
- Число кейсов приемлемо по времени и стоимости прогона; если нет — урезаем **сейчас**, до baseline «до», а не между прогонами
- Ни один плагин не остался без кейсов
- Согласен заморозить набор сценариев до конца спринта

## Риски и допущения

- Генерация тратит время и токены OpenRouter — ключ в `.env`, стоимость фиксируем в логе.
- Плагин может молча вернуть ноль кейсов; поэтому проверка «кейсы по каждому плагину» — обязательный критерий, а не пожелание.
