## Цель

Для каждой находки принять письменное решение о слое защиты с обоснованием и наблюдаемым критерием успеха — без единой строки кода.

**Боль предыдущего шага:** в triage слой защиты указан как «предполагаемый» — он выбирался по горячим следам отчёта. Решение требует взвешивания цены и надёжности. Без этого шага получится набор точечных заплаток: где-то строка в промпте, где-то регулярка в guard, и никто не ответит, почему одну находку закрыли уговором модели, а другую — проверкой в коде.

**Вторая боль: прогон «после» должен уметь подтвердить фикс.** Конфиг заморожен, ассерты в нём — canary, имена инструментов и маркер `[SECURITY_BLOCKED]`. Решение вида «попросим модель отвечать мягче» непроверяемо: прогон «после» не отличит успех от случайности.

## Состав работ

**1. Зафиксировать таксономию слоёв с реальными точками внедрения**

| Слой | Точка в коде | Свойства |
|---|---|---|
| Системный промпт | новая версия в `agent/prompts.py`, выбор в `agent/react_runner.py` | Дёшево, гибко; **не является защитой от prompt injection** — обходится теми же атаками, что тестируем |
| Входной guard | middleware в `factory.py` либо начало `api/routes/chat.py` | Детерминированно, дёшево; ловит явные шаблоны, даёт false positives на легитимных вопросах |
| Выходной guard | `services/agent_service.py`: `run_chat_turn` **и** `_iter_tail_sse_events` | Единственный способ гарантированно не отдать canary и имена инструментов; требует симметрии обоих путей |
| Policy на уровне инструментов | `mcp_client/tool_adapter.py::_run_sync` — все вызовы проходят здесь, `TurnContext` доступен | Самый надёжный слой для действий с побочными эффектами; не зависит от послушности модели |
| Конфигурация приложения | `api/schemas/chat.py`, `api/routes/chat.py`, `core/config.py` | Для векторов вроде `config_id`; дёшево и абсолютно надёжно |

**2. Правило выбора, а не вкусовщина**

- [ ] Принцип: **всё, что приводит к побочному эффекту** — платёж, лид, запрос в Neo4j — чинится в коде (policy или конфигурация); промпт для этого недостаточен
- [ ] Промпт-хардненинг допустим только для тона и тематики: уход из темы, выдуманные обязательства, чрезмерная услужливость
- [ ] Утечка PROTECTED закрывается выходным guard'ом; промпт может дополнять, но не заменять
- [ ] Для каждой находки явно ответить, почему выбран этот слой, **а не соседний**

**3. Решение по каждой находке**

- [ ] Таблица: находка → слой → что конкретно делаем (без кода) → обоснование «почему не другой слой» → наблюдаемый критерий успеха → как это увидит наш assert
- [ ] Критерий успеха формулировать через ассерты замороженного конфига: ответ содержит `[SECURITY_BLOCKED]`, либо canary отсутствует, либо имена инструментов отсутствуют в тексте
- [ ] Группировать находки, закрываемые одним фиксом — только при реальном совпадении механизма, не по похожести названий плагинов

**4. Отдельное решение по вектору `config_id`**

- [ ] Учесть, что поле используется eval-контуром (`evals/`, `EVAL_CONFIGS_DIR`) — простая блокировка сломает существующий процесс
- [ ] Выбрать и обосновать вариант: полностью игнорировать при `SECURITY_ENABLED=true` / требовать внутренний заголовок / сузить до allowlist
- [ ] Зафиксировать, как это проверяется в задаче 12 — ручным кейсом, поскольку в автоматическом наборе поля нет

**5. Границы объёма и явные отказы**

- [ ] Ограничить число фиксов ёмкостью спринта; остальное — `defer` со ссылкой на backlog
- [ ] В `defer` обязательно: rate limiting, защита от абьюза, CORS для production, XSS в `message_html` на стороне клиента
- [ ] Для каждого `defer` — строка «почему не сейчас» и адрес в roadmap
- [ ] Зафиксировать требование к задаче 11: при `SECURITY_ENABLED=false` поведение должно совпадать с baseline «до»
- [ ] Самопроверка по DoD; после «ок» — `summary.md`

## Критерии готовности (DoD)

**Агент проверяет:**

| # | Критерий | Способ проверки |
|---|----------|-----------------|
| 1 | `practice/redteam/fix-decisions.md` существует | `ls` |
| 2 | Строка на каждую подтверждённую находку из `triage-before.md` | сверка перечней |
| 3 | У каждой строки заполнены слой, действие, обоснование «почему не другой слой», критерий успеха | нет пустых ячеек |
| 4 | Критерий успеха выражен через ассерты замороженного конфига | сверка с `promptfooconfig.yaml` |
| 5 | Находки с побочными эффектами не закрыты одним промптом | для платежей, лидов, Neo4j выбран слой policy или конфигурация |
| 6 | Решение по `config_id` принято с учётом eval-контура | раздел про `config_id` |
| 7 | Каждый `defer` имеет обоснование и адрес в backlog | нет `defer` без причины |
| 8 | Зафиксировано требование эквивалентности при `SECURITY_ENABLED=false` | grep |
| 9 | Кода в документе нет — только решения | отсутствие diff по `backend/` и `mcp_server/` |

**Пользователь проверяет:**

- Согласен с принципом «побочные эффекты чиним в коде, не в промпте»
- Объём фиксов реалистичен, список `defer` устраивает
- Согласен с решением по `config_id` и понимает влияние на eval-процесс
- По каждой находке понятно, как прогон «после» докажет работу фикса
- Группировка находок в общие фиксы не выглядит натянутой

## Риски и допущения

- Соблазн закрыть всё промптом — дёшево на вид, но не проверяется ассертами и не держит побочные эффекты.
- Слишком широкий scope фиксов приведёт к тому, что задача 11 не завершится в спринте; лучше меньше фиксов и честный `defer`.
