## Цель

Превратить сырой отчёт в triage-таблицу «находка → категория OWASP → слой защиты», с обязательной строкой на каждый плагин: либо находка, либо обоснованное «не воспроизвелось».

**Боль предыдущего шага:** отчёт Promptfoo — список красных и зелёных строк, а не план работ. По нему нельзя расставить приоритеты и понять, какие находки закрываются одним слоем защиты. Без этого задача 10 выродится в починку случайных симптомов.

**Почему «строка на каждый плагин»:** тишина по плагину неинформативна сама по себе. Плагин мог быть чист потому что агент устойчив, потому что атаки слабые, потому что грейдер не понял ответ на русском, или потому что кейсы не сгенерировались. Это четыре разных вывода с разными последствиями; различить их можно только сверив отчёт с ожиданиями из задачи 07.

**Отдельная ловушка — доверие грейдеру.** Grader это LLM: помечает провалом вежливый отказ и пропускает утечку, завёрнутую в маркдаун. Каждая находка, на которой строится решение о фиксе, требует проверки глазами на реальном фрагменте ответа.

## Состав работ

**1. Сводная картина**

- [x] Таблица по плагинам: число кейсов, провалов, доля успешных атак
- [x] Сопоставить с разделом «ожидания» из `test-review-notes.md`; каждое расхождение прокомментировать — неожиданная чистота подозрительна так же, как неожиданный провал

**2. Triage по находкам**

- [x] На каждую находку — строка: идентификатор кейса, плагин, стратегия, описание наблюдаемого поведения, категория OWASP LLM Top 10, категория OWASP ASI Top 10, severity, предполагаемый слой защиты, ссылка на риск из `threat-model.md`, evidence
- [x] Evidence — короткий фрагмент реального ответа агента. **Значение canary в открытом виде не переносить**: писать «canary присутствует в ответе», иначе токен утечёт в git и потеряет смысл как измеритель
- [x] Предполагаемый слой защиты — из фиксированного набора: системный промпт, входной guard, выходной guard, policy на уровне инструментов, конфигурация приложения

**3. Обязательное покрытие плагинов**

- [x] По каждому плагину — либо находки, либо запись «не воспроизвелось» с одной из причин: агент устойчив, атаки слабые, грейдер не распознал, кейсы отсутствовали
- [x] Для причины «грейдер не распознал» — привести пример, где по нашей оценке атака удалась, а грейдер поставил pass

**4. Ручная верификация ключевых находок**

- [x] Находки высокого severity воспроизвести вручную через `curl` на `/api/v1/chat`
- [x] Пометить каждую строку: подтверждено вручную / доверяем грейдеру / требует проверки
- [x] Отдельно отметить flaky-находки, воспроизводящиеся не каждый раз

**5. Ручные кейсы вне автоматического набора**

- [x] Проверить вектор `config_id`: передать `config_id`, ссылающийся на конфиг с промптом V2 или V3, и зафиксировать, меняется ли поведение агента в платёжном сценарии
- [x] Зафиксировать результат отдельной строкой triage — Promptfoo этот вектор не покрывает по построению
- [x] Самопроверка по DoD; после «ок» — `summary.md`

## Критерии готовности (DoD)

**Агент проверяет:**

| # | Критерий | Способ проверки |
|---|----------|-----------------|
| 1 | `practice/redteam/triage-before.md` существует | `ls` |
| 2 | Сводная таблица по всем плагинам с числами | сверка со списком плагинов конфига |
| 3 | Каждый плагин имеет находки либо «не воспроизвелось» с причиной | нет плагинов без строки |
| 4 | У каждой находки заполнены OWASP LLM, severity, предполагаемый слой защиты | нет пустых ячеек в этих колонках |
| 5 | Каждая находка связана с риском из `threat-model.md` либо помечена как новая | наличие ссылки или пометки |
| 6 | Значение canary в открытом виде отсутствует | grep по значению токена — совпадений нет |
| 7 | Находки высокого severity помечены как подтверждённые вручную | колонка верификации заполнена |
| 8 | Расхождения с ожиданиями задачи 07 прокомментированы | раздел сопоставления |
| 9 | Ручной кейс `config_id` проверен и зафиксирован | отдельная строка в triage |
| 10 | Директория `baseline-before/` не изменилась | пересчёт sha256 отчётов |

**Пользователь проверяет:**

- Согласен с расстановкой severity: приоритеты соответствуют риску для продукта, а не громкости названия плагина
- Согласен с предполагаемыми слоями защиты — это вход в задачу 10
- Убедился, что ключевые находки подтверждены вручную, а не приняты на слово от грейдера
- Согласен с трактовкой «не воспроизвелось» по каждому чистому плагину
- Видит результат по вектору `config_id` и понимает его значимость

## Риски и допущения

- Grader может ошибаться в обе стороны — отсюда обязательная ручная верификация high severity.
- Если baseline подозрительно чистый — проверить по манифесту задачи 08, что eval бил в живой агент и ответы непустые.
- Ручной кейс `config_id` требует знания существующих `config_id` из `evals/configs/` — получить списком, а не угадывать.
